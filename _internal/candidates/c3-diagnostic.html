The framework

Production Readiness Index — eight lenses

Getting a model to answer well in a demo is the easy part. Keeping it correct, affordable, governed, and actually used in daily operations is the work. These are the eight lenses we examine before recommending whether to build, and each one is a place we have seen otherwise-promising projects stall.

Lens 01

Data

An AI system is only as reliable as the records it reads. This lens asks whether the documents, tables, and history the task depends on exist in a form a system can retrieve consistently, rather than living in inboxes and people's heads.

Lens 02

Workflow fit

Automation pays off only when it targets a repeatable, high-volume task with a clear definition of a correct outcome. This lens checks that you have identified a specific workflow rather than a general wish to "use AI somewhere."

Lens 03

Integration

Value shows up when results land inside the tools your team already uses. This lens asks whether the systems of record involved expose an API, an export, or another reliable way in and out, so the AI is not a disconnected side tool.

Lens 04

Evaluation

You cannot ship what you cannot measure. This lens checks for a way to tell whether an answer is good, ideally a set of known correct examples, so quality can be tested before launch and tracked as models and prompts change.

Lens 05

Oversight

Responsible deployment names who reviews the AI's output, when a human stays in the loop, and what happens when the system is unsure. This lens checks that accountability for a wrong answer is defined before the system touches real decisions.

Lens 06

Cost model

Production AI has a per-request cost that scales with usage. This lens asks whether you understand roughly what each run should cost and what a correct result is worth, so the economics are known before volume makes them urgent.

Lens 07

Security

Sending business data to a model carries obligations around where it goes and who may see it. This lens checks that you know which data is sensitive and what your privacy or contractual constraints require before anything leaves your walls.

Lens 08

Team adoption

A capable system that no one trusts or uses returns nothing. This lens asks whether the people whose work changes are involved early and prepared for the new process, because adoption, not the model, is where most value is won or lost.

How an engagement works

From a score to a system

The check is a first read. A real engagement moves in deliberate stages so you never commit to a build before the case for it is written down.

  1. 01

    Assess

    A fixed-fee, time-boxed review of the eight lenses against your actual data and systems. You receive written findings and a clear build or no-build recommendation — including when the honest answer is not yet.

  2. 02

    Build

    If a build is warranted, we agree a fixed scope and a fixed price in writing, then ship it with evaluation gates, oversight, and rollback paths in place from the first release rather than added afterward.

  3. 03

    Operate

    Once live, we monitor quality, cost, and adoption, and improve the system as usage grows and models change. You keep full ownership throughout and can run it yourself whenever you choose.

When we will tell you not to build

AI is not the right answer for every problem, and a stalled pilot is more expensive than an honest no. If the data is not there, the workflow is not well defined, or the value does not clear the cost, we will say so in the Assess findings and recommend against a build. We would rather forgo an engagement than ship a system you cannot depend on.
